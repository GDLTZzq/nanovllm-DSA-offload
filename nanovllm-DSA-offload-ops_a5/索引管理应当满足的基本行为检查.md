# LIDU 索引管理基本行为检查

## 测试对象

1. BF16 路径使用原生 A5 LightningIndexer 生成 Top2048 reference，并验收本仓库 `fused_li_manage(_out)`。
2. C8 路径使用官方 A5 Quant LightningIndexer 生成 Top2048 reference，并验收 `fused_li_manage_c8(_out)` 中的 request-pool update。

## 测试数据

1. index query heads 覆盖 32 和 64，query、key、weights 使用可复现数据。
2. 每个 batch row 的 `candidate_len` 位于 `[2048, 262144]`，source capacity 不超过 18-bit token ID 上限 `2^18`。
3. `req_pool_entries` 是互不重复且合法的 `int32[B]` request-pool row 映射。
4. 长请求恰好有 C 个有效 cache slot；C 是 128 的倍数且 `2048 <= C <= 16256`。`C=0` 请求必须严格 no-op。
5. 有效 cache slot 唯一，值集合恰好为 `0..C-1`，`candidate_len` 以外不得产生有效映射。
6. `miss_count` 位于 `[0, 2048]`，并满足 `miss_count <= candidate_len-C`。

## 每个 batch row 独立验收

1. `topk_index` 包含 2048 个合法且唯一的 token index，其集合与 LightningIndexer reference 相同。
2. `miss_count` 等于构造值，也等于根据 old cache 和实际 `topk_index` 重新计算出的 miss 数量。
3. `topk_index[:miss_count]` 在 old cache 中全部为 `-1`。
4. `topk_index[miss_count:]` 在 old cache 中全部命中。
5. `topk_slots` 全部位于 `[0, C)` 且互不重复。
6. hit 后缀的输出 slot 与 old cache 中的 slot 逐项相等。
7. `new_cache_slots[topk_index[i]] == topk_slots[i]` 对全部 2048 项逐项成立。
8. new cache 的有效 slot 数量、唯一性和值集合 `0..C-1` 保持不变。
9. 未被 `req_pool_entries` 映射的 request-pool row 逐项保持不变。
10. 不恢复 cache 立即进行第二次更新时，`miss_count==0`、cache state 完全不变，全部 Top2048 token 的 slot 映射逐项正确。
11. LIDU 不支持 IOSORT；只要求 miss 在前、hit 在后，不约束两段内部的 token 顺序。
12. `_out` 接口返回的 `topk_index`、`topk_slots`、`miss_count` 和 `cache_slots` 必须分别 alias 调用方传入的持久输出 tensor。

## 18-bit 边界

1. source capacity 和 `candidate_len` 必须覆盖最大合法值 `262144`。
2. 边界用例的 Top2048 必须实际包含 `token_id >= 2^17` 的 token，确保使用到 18-bit token index 的最高位；算子输出仍须与 reference 完整一致。

## Reference 与计时

1. reference 与 LIDU 必须使用完全相同的 query、key、weights、序列长度和 block table。
2. BF16 测试固定执行正确性验收；`--iters=0` 时不计时，`--iters>0` 时随后使用 NPU Event 统计 LightningIndexer 和 LIDU 时延。C8 测试的命令行暂不在本轮调整范围内。
3. 每次计时调用 LIDU 前恢复 initial cache，完成 NPU 同步后再记录 Event 起点，cache 恢复不计入算子时延。
4. `LIDU - LightningIndexer` 只作为索引管理额外开销的代理值，其中还包含 cache pool 访问、workspace 和缓存更新成本。
